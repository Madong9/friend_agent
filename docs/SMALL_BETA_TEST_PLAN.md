# Campus Social Agent 3～4 人体验版测试方案

适用版本：`0.1.0-beta.4`  
测试范围：微信体验版、小程序真实 OpenID、CloudBase、FastAPI、Agent、Matching、通知和站内聊天  
测试性质：小规模功能验收，不作为正式运营数据

## 一、测试目标

本轮使用 3～4 个真实微信号，验证以下完整链路：

```text
微信登录
→ 保存个人画像
→ 发布找搭子需求
→ 后出现的新用户触发候选通知
→ 双方表达感兴趣
→ 形成真实互相匹配
→ 站内双向聊天
→ 关闭并重新打开后数据仍存在
```

同时验证多轮 Agent 对话、无结果放宽、候选反馈和测试用户标识。

本轮不提交正式上线审核，不测试大规模并发，也不以少量样本计算业务结论。

## 二、体验成员准备

1. 在微信公众平台的成员管理中添加每个人实际使用的微信号为体验成员。
2. 将 `0.1.0-beta.4` 设为体验版。
3. 在小范围测试群中发送体验二维码。
4. 每个人必须使用被添加的微信号扫码，不共用微信账号。
5. 昵称可暂时填写为“内测A、内测B”等，不要求填写真实姓名。
6. 不得在画像、聊天或反馈截图中公开手机号、微信号、住址等敏感信息。

建议角色分工：

| 角色 | 人员 | 主要任务 |
|---|---|---|
| A | 发起人/项目负责人 | 先发布需求、接收通知、完成匹配和聊天 |
| B | 体验成员 1 | 稍后加入，触发 A 的新候选通知 |
| C | 体验成员 2 | 测试多轮 Agent、无结果、放宽和候选反馈 |
| D | 体验成员 3，可选 | 与 C 组成第二组真实匹配 |

如果只有 3 人，执行 A、B、C 的任务即可。

## 三、测试前检查

- [ ] 每个人看到的都是 `0.1.0-beta.4`
- [ ] `/auth/wechat` 和 `/users/me` 登录正常
- [ ] “找搭子”“匹配”“我的”页面都能打开
- [ ] 测试用户带有橙色“测试用户”标记
- [ ] 真实体验成员不带“测试用户”标记
- [ ] 手机网络正常
- [ ] B 在 A 完成首次无结果需求前不要打开小程序
- [ ] 有 D 时，D 在 C 完成首次无结果需求前不要打开小程序

## 四、第一组：A 与 B 完整真实匹配

### 4.1 A 先创建画像

A 在“我的”中填写并保存：

| 字段 | 内容 |
|---|---|
| 昵称 | 内测A |
| 校区 | 高新区 |
| 常见活动 | 飞盘 |
| 有空时间 | 周六下午 |
| 社交目标 | 运动搭子 |

保存后退出“我的”页面，再次进入，确认内容没有丢失。

### 4.2 A 发布无结果需求

A 在“找搭子”中发送：

> 周六下午想在高新区找飞盘搭子，轻松一点。

预期结果：

- 当前没有真实飞盘候选人；
- 系统生成一条飞盘 `OPEN` 需求；
- 如果 Agent 询问是否放宽条件，A 暂时不要同意；
- “我的 → 新候选通知 → 我的找搭子需求”中出现飞盘 `OPEN`。

### 4.3 B 稍后加入

A 完成上一步后，B 再打开小程序并填写：

| 字段 | 内容 |
|---|---|
| 昵称 | 内测B |
| 校区 | 高新区 |
| 常见活动 | 飞盘 |
| 有空时间 | 周六下午 |
| 社交目标 | 运动搭子 |

B 保存画像后发送：

> 高新区周六下午有人一起玩飞盘吗？

预期结果：

- B 的候选人中出现 A；
- A 收到“发现新的搭子候选”通知；
- A/B 均没有“测试用户”标记；
- A 原来的飞盘需求保持可查询。

当前版本的候选通知只负责提醒，不会直接跳转到候选详情。A 查看通知后，需要回到“找搭子”重新发送相同需求，才能看到 B。

### 4.4 双向表达感兴趣

按以下顺序操作：

1. B 对 A 点击“感兴趣”；
2. A 重新发送飞盘需求并找到 B；
3. A 对 B 点击“感兴趣”；
4. A/B 分别进入“匹配”页面；
5. “互相感兴趣”区域出现对方；
6. 点击对方，确认出现“开始站内聊天”。

预期结果：只有一方感兴趣时不会建立匹配；双方都感兴趣后才形成真实匹配。

## 五、A 与 B 站内聊天脚本

A 发送：

> 你好，我周六下午想在高新区玩飞盘，你一般几点方便？

B 回复：

> 三点左右可以，我更喜欢轻松一点的局。

A 发送：

> 可以，我们先在站内确认大概时间和校园公共活动地点。

B 回复：

> 好的，周五晚上再确认一次。

检查项：

- [ ] A 能发送，B 能收到
- [ ] B 能发送，A 能收到
- [ ] 对方消息在数秒内出现
- [ ] 退出聊天再进入，历史消息仍存在
- [ ] 关闭小程序重新打开，匹配关系仍存在
- [ ] 不需要交换手机号、微信号等私人联系方式

## 六、C 的多轮 Agent 测试

C 依次发送：

1. `想找个搭子`
2. Agent 追问活动后回答：`攀岩`
3. Agent 追问时间后回答：`周日上午`
4. 如果没有结果并询问是否放宽，回答：`可以`

预期结果：

- Agent 能跨请求保留活动和时间；
- 最后一轮不会重新询问活动类型；
- 放宽后返回候选人，或明确说明仍无结果；
- 页面不会出现 401、503、空白或重复加载。

C 还应分别完成：

- [ ] 对一个候选人点击“感兴趣”
- [ ] 对一个候选人点击“跳过”
- [ ] 对一个候选人点击“不相关”
- [ ] 进入候选详情，确认三个反馈按钮和拉黑、举报入口都存在

第一轮不要让 A/B 互相拉黑或举报，否则会破坏已经建立的真实匹配。

如果确实需要验证拉黑或举报，只允许 C 对明确标记的测试用户操作，并记录目标和时间，便于测试结束后清理。

## 七、可选第二组：C 与 D

如果有第 4 位成员，C/D 可重复 A/B 流程，但使用另一组条件：

| 字段 | 内容 |
|---|---|
| 校区 | 西区 |
| 常见活动 | 攀岩 |
| 有空时间 | 周日上午 |
| 社交目标 | 运动搭子 |

C 先发布需求并保持 `OPEN`，D 后加入并发出相同需求，验证第二组通知、双向感兴趣和聊天不会影响 A/B。

## 八、问题反馈格式

每个问题统一记录：

```text
成员：A / B / C / D
手机型号：
网络：校园网 / Wi-Fi / 5G
操作步骤：
输入内容：
预期结果：
实际结果：
等待时间：
是否可重复：
截图：
```

问题反馈中禁止包含：

- OpenID
- JWT 或任何 Token 内容
- Publishable Key
- 微信 AppSecret
- CloudBase 后端 API Key
- `.env` 文件内容
- 用户私人联系方式

## 九、第二天复测

测试后的下一个自然日，每位成员重新打开小程序并检查：

- [ ] 自动登录正常
- [ ] 画像仍然存在
- [ ] 找搭子需求仍然存在
- [ ] 通知读取状态正确
- [ ] 真实匹配仍然存在
- [ ] 聊天历史仍然存在
- [ ] 再发送一次找搭子请求可以正常返回

## 十、结果汇总

测试结束后，在项目根目录执行只输出聚合数据的统计脚本：

```bash
./.venv/bin/python scripts/beta_metrics.py
```

同时人工汇总：

- 登录成功人数
- 完成画像人数
- 有效找搭子请求数
- 返回真实候选的请求数
- 新候选通知成功次数
- 真实双向匹配数
- 成功发送的聊天消息数
- 401、403、503 和超时次数
- 前三个高频体验问题

不要把 3～4 人的比例当作正式业务指标，本轮只判断主链路是否可靠。

## 十一、进入下一轮的标准

满足以下条件后，再扩展到 5～10 位体验成员：

- [ ] 3～4 位成员连续两天都能登录
- [ ] 未发生用户串号或看到他人私有数据
- [ ] 至少完成 1 组真实双向匹配
- [ ] 至少完成 1 次新候选通知闭环
- [ ] 真实匹配双方可以双向聊天
- [ ] 无持续出现的 401、503 或请求超时
- [ ] 画像、需求、匹配和消息在重新打开后没有丢失
- [ ] 没有未处理的隐私或安全问题

若出现串号、隐私泄露、越权访问或大面积登录失败，应立即停止体验测试；一般布局和文案问题记录后进入下一版本集中修复。
